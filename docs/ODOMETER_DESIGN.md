# 虛線週期碼表:設計說明(管線 B 自車速)

> 依 2026-09-18 的 [`tools/dashcam_range_speed.py`](../tools/dashcam_range_speed.py) 整理。本文件只講**怎麼量、為什麼這樣量、哪些做法已放棄**。
> 精度數字見 [../README.md](../README.md)「驗證摘要」,失效邊界見 [`docs/FAILURE_BOUNDARIES.md`](FAILURE_BOUNDARIES.md),
> 各案取樣點與參數見 [`docs/CASE_PARAMETERS.md`](CASE_PARAMETERS.md)。

## 0. 原理與誤差來源

法定虛線(漆線 + 間隔)以固定週期 `cycle_m` 流過畫面上固定的一列,該處的局部亮度就以 `v / cycle_m` 的頻率振盪。
量出以幀為單位的週期 T,就得到 `v = cycle_m × fps / T`。

輸入只有兩個常數:法定週期與幀率。不經過 SHARP、地面平面、尺度錨或畸變校正,所以距離修正係數完全不影響自車速
([`tools/public_dataset_ego_eval.py`](../tools/public_dataset_ego_eval.py) 只 import `pick_points`、`dash_cycle_speeds`、`extract_odometer_signals`)。
系統性誤差主要有三個來源:

1. **T 選錯倍數**(八度錯:鎖到半週期或倍週期)→ 第 1.4 節;
2. **cycle 常數錯**(規範值 ≠ 實測,或片段跨路類)→ 第 2.1 節;
3. **fps 錯**(容器謊報、VFR、剪輯跳接)→ [`data/output/dashcam_validation/README.md`](../data/output/dashcam_validation/README.md) 的三種時基陷阱。

另有兩類由防護鏈與窗長處理:訊號被非法定圖樣或震動汙染(換道時掃過匝道短線、近停時旁車流過搜尋帶、引擎震動;
鎖到的週期不一定剛好差一個八度,例如真速 82 讀成 146),見第 1.5 節;以及加速段的窗內平均
(解析度約 3 s,見 [`docs/FAILURE_BOUNDARIES.md`](FAILURE_BOUNDARIES.md))。

## 1. 現行設計

| 階段 | 位置 |

### 1.1 訊號抽取

- 每幀取局部對比 `g − GaussianBlur(g, 51×51)`(比周圍路面亮多少),不受整體照度變化影響。
- 每個取樣點 (x, y) 取一條橫帶:縱向 y±6(13 列)、橫向 x±`band_px`(預設 120),逐欄平均。每幀輸出兩個數:
  脈衝強度(帶內最大值 − 中位數)與脈衝橫向位置(最大值所在欄相對 x 的偏移,給線位穩定閘與雙線偵測用)。
- 用橫帶而不是單一像素,是因為車在車道內橫向漂移,固定像素會滑出漆線。
- `band_px` 120 是對 1920 寬的台灣行車紀錄器定的,原則是不超過取樣列上一個車道的影像寬度
  (1164 寬的廣角相機遠列兩條線只隔約 175 px)。線位穩定閘的門檻隨 `band_px` 等比例縮放。

### 1.2 取樣點

- 點要落在**虛線**上;實線沒有週期訊號(hs005 右側是實線,所以只取左側)。
- 同一條線上取 3–4 個**不同列**(遠到近):跨列相位閘要不同列才能判斷,多點共識與分裂鎖閘至少要 2 點。
  左右兩條虛線可以都取(wow001),但距離校正只配對同一條線上的點
  (同線分組閘,理由見 [`tools/odometer_distance_calib.py`](../tools/odometer_distance_calib.py) 的 `group_by_line`)。
- 自車有換道的片:先畫線位軌跡圖,挑駐留平台,避開連續縱向亮痕(dc003)。
- 各案點位記在 [`docs/CASE_PARAMETERS.md`](CASE_PARAMETERS.md)。**沒記錄的點位等於不能重現。**
- 自動挑點:[`tools/auto_odometer_points.py`](../tools/auto_odometer_points.py),資料集級評估的前提。hs005 與人工點實質等價;
  dc003 自動版覆蓋高很多但尾巴大,**換道段是否過度發話尚未仲裁**
  (見 [`data/output/comma2k19_eval/README.md`](../data/output/comma2k19_eval/README.md) 第五節)。

### 1.3 自相關取週期

對每一幀,以該幀為中心取長 W 的窗(`--odometer-window-s`,預設 3.0 s),訊號去均值後算正規化自相關 `ac`:

- lag 搜尋範圍 0.25–3.0 s(10 m 週期約對應 3–40 m/s),上限再壓到半窗長,確保窗內至少兩個完整週期;
- 從自相關的**第一個局部極小**開始找峰(跳過中央瓣:一根漆線通過要好幾幀,中央瓣的肩會被當成短週期);
- 範圍內的 argmax 當初始 lag,交給基頻選擇。

⚠ 有限窗自相關的峰高隨 lag 衰減,`ac[2L]/ac[L] ≈ (W−2L)/(W−L)`(乾淨巡航約 0.85)。
所以直接比較不同 lag 的峰高會偏向短週期,拿這個比值跟固定門檻比也會誤判八度(第 3.1 節)。

### 1.4 基頻選擇(八度問題),三層

**(a) 諧波梳狀評分 `_comb_score`(2026-07-24)。**
候選 {argmax/2, argmax, 2·argmax},每個先用 `_peak_snap` 吸附到 ±2 幀內真正的局部峰,不是局部峰就丟掉
(例如乾淨巡航時 argmax/2 落在反相谷)。分數 = 候選週期 P 的整數倍處 `ac` 平均 − 半整數倍 (k−½)P 處 `ac` 平均:

- 真基頻:整數倍是峰、半整數倍是谷,分數高;
- 諧波 P = T/2:它的半整數倍落在真峰 T、2T 上,分數低;
- 子諧波 P = 2T:它的半整數倍落在真峰 T、3T 上,分數低。

一次評分同時排除上下兩個八度,不需要加倍/減半鏈。

**(b) 雙線覆寫 `_dual_line`(2026-07-24)。**
亮度自相關分不出「一條線走半週期」與「兩條交錯的線(自車道 + 鄰車道)各走全週期」,但後者的脈衝會在兩個
橫向位置之間交替。判定條件:脈衝(強度 ≥ max(10, 0.4 × 最大值) 的局部峰)至少 4 個,依橫向位置中位數分兩群,
兩群間距 ≥ 6 px 且 ≥ 2.5 倍群內標準差,相鄰脈衝換邊比例 > 75%。成立時每條線的週期 =
**2 × 實測脈衝間距中位數**,不是 2 × argmax(高速時 argmax 已經落在每線週期上,加倍會過修),
再用 `_peak_snap` 吸附到自相關的局部峰;吸附成功時它是該幀唯一的候選,下一層不得覆寫
(它是幾何的直接觀測,不是峰之間的偏好);吸附失敗時退回 (a) 的梳狀評分。

條件照設計是嚴格的(單一條漂移的線不應觸發,否則速度會減半)。實測在高速公路上仍偶爾觸發
(dc002 61、dc003 17、dc006 21、dc007 13 次),但 2×間距吸附後多半落回 argmax,淨改變近零(dc002 changed 僅 2);
真正修到的是合成的「鄰道虛線 + 低速」情境
(見 [`data/output/odometer_lag_audit/README.md`](../data/output/odometer_lag_audit/README.md)「2026-07-24 重構完成」)。

**(c) 跨時間聯合選擇 `_join_octaves`(2026-08-17,現行預設)。**
單窗內有時真的無解:夜間逆反射標記讓半週期成為真峰,五個形狀特徵都分不開(第 4 節)。
但車不可能在兩幀之間速度加倍,所以對每個取樣點沿時間跑 Viterbi:

- 狀態 = 該幀的候選 lag,只來自該幀自相關真有的峰,不無中生有;
- 發射 = 梳狀分數 − 該幀最佳分數(只比較同一幀內的偏好,各幀等權);
- 轉移 = `−20 × max(0, |ln(L_前/L_後)| − r/fps)`,r = `--max-rel-change-per-s`(預設 1.5)。
  每幀免費的 |Δln v| 上限是 r/fps(30 fps 時為 0.05),遠小於一次八度跳躍的 ln 2 = 0.69;
  而每秒 1.5 的對數變化率遠高於任何真實車輛的加減速;
- 沒有候選的幀把鏈切斷,一段讀不到的區間不會把選擇傳過去。

一次八度切換的代價約 `20 × (ln 2 − r/fps)`(30 fps 時約 12.9),所以「跳八度一秒再跳回」變得很貴;
持續 ≥ 3 s 的真實八度改變仍會跟上,且切換點落在正確的邊界幀。

**轉移項必須尺度不變:罰 |Δ ln v|,不是 |Δv|。** 低一個八度的路徑,速度變化也低一個八度、看起來永遠更平滑,
所以罰絕對 |Δv| 等於獎勵減半(第一版就這樣把台灣封存打壞,數字見 [`docs/FAILURE_BOUNDARIES.md`](FAILURE_BOUNDARIES.md))。
改罰對數之後,真值路徑與減半路徑代價相同,八度交回沿整段累積的梳狀證據決定。

效果與迴歸見 [`data/output/comma2k19_eval/README.md`](../data/output/comma2k19_eval/README.md) 4b 與 FAILURE_BOUNDARIES:
comma2k19 夜間的數字屬 Chunk_1 舊選段的診斷分層,**不是可引用的精度數字**;台灣 15 案開啟後 12/15 案零變動,
hs005、hs006s(有人工逐幀真值)零變動。`--no-join-octaves` 回到逐幀獨立選擇,可重現 2026-08-17 以前的封存輸出。
(程式 `--no-join-octaves` 的 `--help` 寫 MAE 13.9 → 4.5、p90 88.3 → 3.4,與 README 4b 的 12.46 → 4.72、76.66 → 3.58 不同,
以 README 4b 為準,help 文字待改,見第 6 節。)

### 1.5 防護鏈

每一道都是實際失效換來的。依執行順序(前四道在 pass 1 逐點,其餘在 pass 3 與 `main()`):

| 閘 | 條件(不過就不發話) | 擋什麼 |
|---|---|---|
| 訊號強度 | 窗內訊號 std < 2 → 該點跳過 | 停車時虛線停在帶內,成為近乎常數的高訊號,殘差雜訊自相關出荒謬速度 |
| 線位穩定 | 窗內強度 > 10 的幀 ≥ 4 幀時,這些幀的橫向位置 IQR > 50 px(隨 `band_px` 縮放)→ 跳過 | 換道時搜尋帶掃過匝道密集短線,穩定錯鎖(真速 82 讀成 146) |
| 窗內 ≥ 2 週期 | lag 上限 ≤ 半窗長 | 慢速爬行的單週期假峰;低於對應速度就誠實不發話 |
| 跳過中央瓣 | 從第一個局部極小開始找峰 | 漆線通過寬度造成的中央瓣肩被當成短週期 |
| 峰突出度 | `ac[lag] − ac[第一個極小] ≥ 0.3` | 非週期突發訊號的寬肩(約 0.00–0.03;真鎖 0.7 以上) |
| 信心 | `ac[lag] ≥ 0.25` | 弱峰 |
| 跨列相位 | 不同列的點兩兩互相關(最多 3 對),若全部峰在 \|offset\| < 2 幀 → 整幀清空 | 引擎/手把震動:週期性且全域同相;真虛線是先遠列、後近列 |
| 分裂鎖 | 各點讀值最大/最小 > 1.5 → 只留中位數 ±25% 內的多數群,不足 2 點就拒發 | 兩個不可調和讀值的「中位」其實是平均,給出幻速(34 與 98「一致」成 69) |
| 多點共識 | 取各點中位數 | 單一點滑到裂縫或鄰線 |
| 雙窗一致 | 3.0 s 與 5.1 s 兩窗各跑一次完整流程,差 ≤ 12% 取平均 | 八度錯與加速抹糊對窗長敏感,真鎖不敏感 |
| 強鎖免雙窗 | 短窗 conf ≥ 0.5 且突出度 ≥ 0.5 → 單獨採用短窗值 | 短片減速段長窗平均漂走,雙窗閘會誤殺乾淨的鎖 |

### 1.6 次幀拋物線內插

選定整數 lag 後,用三點拋物線求峰頂,速度一律用 `lag_f` 算(`v = cycle × fps / lag_f`):

```
lag_f = lag + ½ · (ac[lag−1] − ac[lag+1]) / (ac[lag−1] − 2·ac[lag] + ac[lag+1])
```

只讀 argmax 那一行會誤以為碼表用整數 lag;2026-08-02 曾據此提過「高速要加次幀內插」的待辦,查證後早已存在,撤回。

### 1.7 停止、內插與輸出

- **停止**:路面帶(縱向從畫面高 55% 處到下緣,下緣取 hood 線與畫面底部往上 80 px 兩者中較高的一條;橫向取中間一半寬度)
  相鄰幀差 > 14 的像素比例,偵測框遮掉他車,0.5 s 中位濾波後 < 0.02 為停止候選。兩道否決:任何通過閘的碼表讀值優先
  (停車時漆線不可能流過);碼表帶訊號活動度(各點 ±0.5 s 內 std 的最大值)≥ 3 也否決。停止 → 0 km/h。
- **內插**:片內(不含片頭片尾)≤ 2 s 的無讀值空隙線性內插;更長的空隙與片頭片尾的空白在這一步維持空值。
- **平滑**:最後做約 1 s 的滾動中位數(窗長取 fps 的奇數,忽略 NaN):孤立壞窗(換道、磨損漆線)拖不動曲線,
  真實加速仍通過。副作用:窗內只要有任一有值的幀就會輸出數值,所以每段未內插的長空隙兩端、以及片頭片尾的空白,
  各約 fps/2 幀(約 0.5 s)會被填上鄰近讀值。
- 輸出 `ego_speed.csv`:`frame_idx, t_s, ego_visual_kmh, method`,method 為 `dash_odometer` / `stopped` /
  `interpolated` / `none`。⚠ 上一點被滾動中位延伸的列,method 仍是 `none` 但**有值**;
  所以「無讀值(no lock)」要看 `ego_visual_kmh` 是否為空,不能看 method(程式側待修,見第 6 節)。
- 光流在任何地方都不給速度值(第 3.2 節)。

## 2. 兩個前提:週期常數與取樣率

### 2.1 週期勿信規範先驗

- 規範:一般道路 4 m 線 + 6 m 空 = 10 m;高速公路 4 + 8 = 12 m。
- 實測支持台灣國道與高架是 **10 m**:國1(dc006)、台86 高架(dc007)經 GPS OSD 反驗都是 10 m;
  hs005(國道)以 cycle 10 對人工畫格真值 MAE 0.69(見 [../README.md](../README.md)「驗證摘要」)。
  旁證:國3(wow001)改用 12 m 明顯更差,但該片自車速本身未過驗證
  (見 [`data/output/dashcam_demo/wow001/README.md`](../data/output/dashcam_demo/wow001/README.md))。
  台灣 demo 全部用 `--dash-cycle-m 10`。(`--dash-cycle-m` 的 help 文字仍寫高速公路 12 m,以實測為準。)
- 反驗方法:有 GPS OSD 時,脈衝間隔幀數 = cycle / v × fps;10 與 12 差 20%,分得開。
  公開資料集用 `--solve-cycle` 以真值反推:comma2k19 得 14.37 m(CAN)/ 14.52 m(位姿),
  對上 Caltrans 高速公路的 14.63 m,排除全國 MUTCD 預設的 12.19 m。
- 週期是**每條路**的常數,不是每支片的常數。碼表量到的是真實週期;片段跨路類時錯的是餵進去的常數,
  交界處會系統性倍速(見 [`docs/FAILURE_BOUNDARIES.md`](FAILURE_BOUNDARIES.md) 第一、二條)。

### 2.2 取樣率下限

每個週期要 ≳ 8 幀,即 `fps ≳ 8 × v / cycle`(換算:10 m、30 fps 可到約 135 km/h;14.63 m、20 fps 約 132 km/h)。
低於此時 ½ 與 2× 的假峰都落在搜尋範圍內,梳狀評分分不開;加大視窗反而更糟。
KITTI 10 Hz 的案例與成功案例的幀/週期範圍見 [`docs/FAILURE_BOUNDARIES.md`](FAILURE_BOUNDARIES.md)。

## 3. 已廢棄的機制與原因

### 3.1 八度防護 + sub-octave 的加倍/減半鏈(07-24 移除)

八度防護(門檻寫死 0.75,最多連續加倍兩次)從首版 07-09 就有;07-11 把門檻參數化為 `--octave-threshold`
(預設 0.75,舊案結果不變)並加入 sub-octave 修正:

- **八度防護**:`ac[2L]/ac[L]` 超過門檻就把 lag 加倍。乾淨巡航時有限窗衰減本身就讓比值約 0.85 > 0.75,
  會系統性翻成半速,所以帶內不可能有第二條線的案改用 0.95(dc003/dc006/dc007)。
- **sub-octave 修正**:國道貓眼每隔一根漆線(20 m 子結構)讓 argmax 直接選 2L(半速);若 lag/2 處也是局部峰
  且 ≥ 0.6 × `ac[lag]`,就取 lag/2。它在真實素材上確實救回過一次:dc008 封存輸出 t≈18.4 s 的半速錯
  (舊 28.4 km/h,GPS OSD 57)在 07-11 sub-octave 修正後已讀 56.9;07-24 重構後仍維持修好,現行輸出同樣是 56.9。

為什麼拆掉(2026-07-16 稽核,[`data/output/odometer_lag_audit/README.md`](../data/output/odometer_lag_audit/README.md)):

- 五支 demo 上八度防護觸發後被 sub-octave 撤銷的比例是 98–100%,threshold 0.75 與 0.95 的最終輸出中位差 0.00:
  正確的結果靠兩個錯誤互相抵銷,防護與旗標實質是死碼。
- 它該防的「鄰道虛線 + 真速 ≲ 77 km/h」情境仍會漏出高信心的雙倍速(合成測試:真 54 讀成 108)。

取代者是第 1.4 節 (a)(b);重構的逐幀迴歸(五支 demo 與 20251029 批量六案 median|Δ| 0.00、合成鄰道 54 → 54.0)見同一份稽核 README。

殘留:`--octave-threshold` 仍被接受,但完全不影響結果,只為讓舊指令能跑;[`docs/CASE_PARAMETERS.md`](CASE_PARAMETERS.md) 裡
dc003/dc006/dc007 帶的 `--octave-threshold 0.95` 同理。

### 3.2 光流

- **當速度來源或備援**:早期版本在無虛線時用 LK 光流當備援。已移除:震動與夜間會把 60 km/h 讀成 2。
  現在沒有碼表讀值就是 no lock,不拿光流補。
- **當停止判定**:舊版用 LK 特徵點位移判停止,但角點會黏在擋風玻璃反光上(任何車速下都像素不動),
  曾把 70 km/h 的夜間行駛判成停止。已改成第 1.7 節的路面帶幀差。

### 3.3 逐幀獨立的基頻選擇(2026-08-17 起不是預設)

每幀每點獨立取梳狀最高分,沒有時間約束,鎖定可以掉到半速一秒再回來。現在只在 `--no-join-octaves` 下使用,
用途是重現封存輸出。

## 4. 試過失敗,不要重試

| 做法 | 當時的想法 | 結果 |
|---|---|---|
| 跨列相位「速度」閘 | 用跨列相位差(時間差)推速度,與碼表讀值互相把關 | 週期訊號的跨列互相關多峰,分不出哪個峰是真的時間差,會誤殺好段;已拆除 |
| 脈衝形狀判別器(含「脈衝寬度匹配濾波」) | 漆線與路釘的脈衝形狀不同,可在單窗內認出半週期鎖 | 時間形狀四特徵(寬度/峰銳度/面積/振幅)在誤鎖窗不比正確窗更交替(相鄰對一致率 0.53–0.72,擲硬幣 0.50);縱向跨列高度只差 6.0 vs 7.0 列(夜間長曝光把點狀路釘拖成條紋);幹道段根本沒有交錯。單窗內無解,改走第 1.4 (c) |
| `_join_octaves` 轉移項罰絕對 \|Δv\| | 罰速度變化量就能擋八度跳躍 | 等於獎勵減半,台灣封存被打壞(原理見第 1.4 (c),數字見 FAILURE_BOUNDARIES) |
| 縮窄搜尋帶治倍速(±120 → ±60 px) | 倍速是帶子跨到隔壁車道線 | comma2k19 三段失敗案 MAE 幾乎沒變 |
| 加大視窗救低取樣率 | 長窗包含更多週期、峰更穩 | KITTI 正確群 52% → 20% → 15%,長窗給倍週期別名更多支持 |

後三列的數字與對照表見 [`data/output/comma2k19_eval/README.md`](../data/output/comma2k19_eval/README.md) 4c 與 [`docs/FAILURE_BOUNDARIES.md`](FAILURE_BOUNDARIES.md)。

跟第一列不要混淆的兩件事:現行的跨列相位閘只問「是不是所有列對都同相」(判震動),不從相位推速度;
[`tools/odometer_distance_calib.py`](../tools/odometer_distance_calib.py) 也用跨列互相關,但把 lag 限在 0–0.95 個週期內、對整段片取值,
用途是量前向距離尺度,不是逐窗把關速度。

## 5. 設計層面仍未解

1. **跨路類的週期改變不會被旗標**(comma2k19 車 2 的高速連接道:實際週期約 10 m,假設 14.63 m)。
   讀碼後的精確描述:轉移項對任何超過 r/fps 的對數階躍都收費,不只八度(FAILURE_BOUNDARIES
   寫「只對八度跳躍收費」不精確)。真正的漏洞有兩個:候選只來自 {½, 1, 2} × argmax 吸附到的峰,
   某幀所有候選都落在新週期上時,沒有「維持舊速度」可選;收費之後也不留任何旗標。
   該段實測 648 個連續幀對中只有 11 個 |Δ ln v| > 0.05,最大 0.54 在交界;中間約 700 幀**穩定地**錯在
   約 140 km/h(真值約 96)。所以階躍閘只能標出「交界兩側有一側錯」,判斷不了是哪一側;
   設計應該是「標記斷點,再把兩側整段降級或逐段反推週期」,不是加重扣分。未實作;前置條件是迴歸評分器進版控。
2. **夜間半週期殘留**:Chunk_1 舊選段的夜間仍有 3.2% 半週期幀,整段持續鎖在路釘週期時,連續性反而幫它站穩。
   五個形狀特徵已否證(第 4 節),要再進步需要新的獨立線索,目前沒有候選。
   在事前選段(2.18 那組)下,車 1 夜間 1.69 反優於日間 2.14
   ([`data/output/comma2k19_eval/README.md`](../data/output/comma2k19_eval/README.md) 4-2-3),所以這一項優先度低。
3. **自動挑點在換道段是否過度發話**:未仲裁,見第 1.2 節。
4. **wow001 自車速未過驗證**:見 [`data/output/dashcam_demo/wow001/README.md`](../data/output/dashcam_demo/wow001/README.md)。
