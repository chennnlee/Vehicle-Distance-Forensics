## 2. 環境:為什麼要另開一個 venv

六個 repo 的依賴**互相衝突**,無法裝在同一個乾淨環境裡:

| 衝突 | 實際狀況 | 處理方式 |
|---|---|---|
| `numpy` 版本 | depth-pro 釘 `numpy<2`、DA3 也釘 `numpy<2`,但 opencv-python 4.13 要 `numpy>=2` | 裝 numpy 2.5.3。實測兩個模型都正常運作,那兩個 pin 是保守值 |
| Python 版本 | DA3 的 `requires-python` 是 `>=3.9,<=3.13`,而 `<=3.13` 在 PEP440 下**不含 3.13.11** | `pip install --ignore-requires-python` |
| `open3d` | Python 3.13 沒有 wheel。但它只給視覺化用,推論不需要 | `--no-deps` 安裝後手動補推論真正需要的套件 |
| `moviepy.editor` | moviepy 2.x 移除了這個子模組,DA3 在 `utils/export/gs.py` import 它 | 在 `depth_backends.py` 裡塞 shim,**不修改 vendored 原始碼** |

所以環境建在 `~/venvs/depthbench`,用 `--system-site-packages` 繼承 base 的 torch
(省 3 GB 重新下載,也保證 CUDA 版本一致)。

### 2.1 重建環境的完整指令

```bash
python3 -m venv --system-site-packages ~/venvs/depthbench
V=~/venvs/depthbench/bin

$V/pip install torchvision --index-url https://download.pytorch.org/whl/cu130
```


### 4.1 `smoke` — 先確認裝好了

```bash
$P tools/depth_model_benchmark.py smoke --image data/input/sample.jpg
```

### 4.2 `run` — 在影格上量目標距離

需要一份 targets CSV,每列是「哪一幀的哪個像素」:

```csv
frame_idx,px,py
592,640,430
593,641,431
```

```bash
$P tools/depth_model_benchmark.py run \
   --model depth_pro \
   --frames /tmp/seg21_frames --frame-glob "f{frame}.jpg" \
   --targets seg21_targets.csv \
   --out data/output/depth_benchmark/seg21_depth_pro.csv
```

取樣用**該像素周圍 5×5 的中位數**而不是單一像素:車輛下緣正好是深度不連續處,
單點讀值一個壞像素就可以差好幾公尺;中位數穩定,又不像平均值那樣跨越邊界糊掉。

## 5. 評估協定:為什麼一定要報 raw 與 scaled 兩欄

這是整個實驗設計裡最重要的一點。

- **`raw`** = 模型輸出的公尺直接拿來比。回答:**絕對尺度對不對**。
- **`scaled`** = 先乘上一個全域常數(取 `median(真值/預測)`)再比。這是深度文獻的標準
  median-scaling 協定。回答:**相對幾何對不對**。

兩欄一起看才能把兩種完全不同的失效分開:

| raw | scaled | 意義 |
|---|---|---|
| 差 | **好** | 幾何是對的,只有絕對尺度錯 → **法定標線尺度錨正好能修好**,這是支持本計畫方法的證據 |
| 差 | 差 | 相對幾何也錯 → 再怎麼錨定都救不回來 |

Depth Anything V2 是 affine-invariant **視差**,根本沒有公尺,所以只有 `scaled` 欄
(用最小平方擬 `depth = 1/(a·disp + b)`)。這正好示範計畫書講的「尺度歧義 Scale Ambiguity」。

### 指標

`AbsRel` / `RMSE` / `δ1` 是深度文獻標準指標(審稿人要看的);
`中位誤差%` 是本專案的報法,**可以直接跟雷達近場的 7.0% 對比**。

## 7. 已經看到的第一個結果(smoke 階段,5/5 backend 全部跑通)

同一張 `data/input/sample.jpg`(2048×1362),**同一台相機、同一個場景**,五個模型的輸出:

| backend | 類型 | 預測 fx | fx/寬 | 深度範圍 | **中位深度** |
|---|---|---|---|---|---|
| `depth_pro` | 度量 | 6575.5 px | **3.21** | 10.2 – 10000 m | **103.11 m** |
| `unidepth_v2` | 度量 | 3634.7 px | **1.77** | 13.9 – 579.8 m | **74.51 m** |
| `metric3d_v2` | 度量(給定內參) | 1629.2 px | 0.7955(我們餵的) | 3.7 – 147.4 m | **29.97 m** |
| `da3_metric` | 度量 | 不輸出 | — | 2.2 – 80.1 m | **22.75 m** |
| `depth_anything_v2` | **相對** | 不輸出 | — | 0 – 816.8(無單位) | — |
| (SHARP 的固定假設) | — | — | 0.7955 | — | — |

**兩個最直接的觀察:**

1. **四個度量模型對同一張圖的中位深度是 22.75 / 29.97 / 74.51 / 103.11 公尺——差 4.5 倍。**
2. **兩個會自估內參的模型對同一台相機的焦距差 1.81 倍**(3634.7 vs 6575.5),
   而且都遠離 SHARP 的固定假設 0.7955×寬。

這與 CLAUDE.md 既有的記錄同向:

> UniDepth v2 對 hs005 預測 fx=843(等於距離修正係數 0.53),比實測的 0.76 還過頭;
> SHARP 假設 1527(係數 1.0)則偏另一邊。→ **兩個模型的內參都不可信,物理量測才可信**

⚠ **這張圖不是有真值的評估素材**,上表只證明「模型之間彼此嚴重不一致」,**不能證明誰對誰錯**。
要判定誰對誰錯必須用 §4.2/4.3 的流程對雷達真值跑。但「四個 SOTA 模型差 4.5 倍」這件事本身
已經足以說明:**在沒有物理錨點的情況下直接採信任何單一模型的公尺數,是沒有依據的**——
這正是計畫書階段一要定義的「失效邊界」。

## 9. 已知限制(先寫下來,免得之後當成新發現)

1. **深度圖給的是沿光軸的 Z,不是沿射線的 range**,而雷達給的是縱向距離。
   目前直接以 Z 對比縱向距離,在前視、俯仰小的行車紀錄器視角下差異很小,
   但若要做嚴謹版本應由內參轉換。
2. **取樣點的定義會影響結果。** 目前在 targets CSV 指定的像素上取 5×5 中位數。
   要跟管線嚴格可比,targets 應由**同一組 YOLOv8m-seg 遮罩的接地點**產生
   ——否則比到的是「取樣點差異」而不是「深度模型差異」
   (這正是 2026-09-16 偵測器受控比較踩過的坑)。
3. **`metric3d_v2` 需要內參**,無內參時本工具沿用 SHARP 的固定 FOV 假設
   (`fx = 0.7955 × 寬`)。這是刻意的:讓它與 SHARP 的假設一致,量出的就是那個假設的代價。
4. **`da3_metric` 權重是 Apache 2.0、可商用**(2026-09-21 三方查證:HF model card 的 license 欄、
   HF API 的 `license:apache-2.0` 標籤、`depth_models/Depth-Anything-3/LICENSE`)。
   ⚠ 本行在 2026-09-21 之前寫成 CC BY-NC 4.0,那是錯的(錯誤來自我方 backend 的字串);見 §3。
5. Video-Depth-Anything 已 clone 且 import 通過,但**尚未寫成 backend**
   ——它是影片模型,介面與逐幀模型不同(需要整段一起餵),要另外處理。

## 11. 修過的一個 adapter bug(2026-09-16,記著別重蹈)

**`da3_metric` 一開始把 `pred.depth` 直接當公尺讀,那是錯的。**

`DA3METRIC-LARGE` 輸出的是**canonical depth**,不是公尺。它的 model card 寫
"multiplying by focal length gives metric depth",repo 自己的
`utils/alignment.apply_metric_scaling()` 把公式寫死了:

```python
focal_length = (intrinsics[..., 0, 0] + intrinsics[..., 1, 1]) / 2
return depth * (focal_length / 300.0)
```

而 `DepthAnything3.inference()` **不會**替你套用 —— 它回傳 canonical 張量,而且
`pred.intrinsics` 是 `None`、`pred.scale_factor` 是 `None`、`pred.is_metric` 是 `{}`。
所以呼叫端必須自己乘。修正前後在同一台前車上差 **8.68 → 11.60 m(+34%)**。

**兩個延伸結論:**

1. **DA3METRIC 不是 camera-agnostic。** 它跟 `metric3d_v2` 一樣需要焦距,
   它的「公尺」會完整繼承那個焦距的誤差。真正自估內參的只有
   `depth_pro` 與 `unidepth_v2` 兩個。
2. **教訓:模型「輸出公尺」這件事不能憑 API 欄位名稱認定。** `pred.depth` 這個名字
   看起來就是深度,實際是 canonical 值。**必讀 model card 與原始碼的後處理**。

## 14. ✅ 第 3 項:接地點不可用時,哪一種方法還活著(2026-09-16)

### 14.1 為什麼要測這個

精度上深度模型打不贏幾何管線(2–4% vs 7.0%,而且還不是同條件)。
所以「深度模型的價值」不能建立在準度上,要建立在**幾何法做不到的事**上。

幾何法的地面平面公式 `d = A/(py − y_h)` **只對地面上的點成立**。
本專案已記錄過三個因此失效的情境:貼身目標車接地點低於 hood 線、
擦身而過時接地點沿車身遷移、急煞俯仰破壞平面假設。

### 14.2 實驗設計

⚠ 原本想找「底部被他車遮擋」的真實案例,**盤點後放棄**:高速公路跟車畫面裡
前車就是最近的物體,seg21 的 100 幀裡只有 1 幀符合;而「接地點低於 hood 線」
在這台相機上不存在(8.4 m 的車接地點還在 py≈503,離 hood 線 700 很遠)。

改成一個**直接而且可控**的測法:同一台車、同一組影格、同一個雷達真值,
只把取樣點從**接地點**換成**車身中心**(遮罩像素的中位位置)。
車身中心比接地點高 **17–23 px(中位)**,而且**永遠看得見**——
接地點被擋住時你還有它。

## 15. 方法 C:純古典幾何標定(2026-09-16,**2026-09-17 更正**)

> ⚠ **更正摘要**(經過與證據見 §18)
> 原本報的 **A = 1153 / 1139 是舊工具讀取範圍兩端造成的假訊號,不是量測**。
> 下列三項**全部撤回**:「兩段 A 吻合 1.2%」、「Δ 由兩段獨立求出 1.90 / 1.75 m,等於物理安裝距離」、
> 「方法 C 對雷達近場 3.03 / 3.72%」。
> 改用「虛線在兩列之間的時間差」量 A 之後,方法 C 的誤差**取決於兩個尚未定案的選擇**
> (接地點怎麼取、雷達與相機的偏移 Δ),落在 **2.5% 到 18.8%** 之間。

### 15.1 定位

報告要比較三種方法,差別只在**地面幾何從哪裡來**:

| | 方法 | 地面幾何 | 尺度 | 學習成分 |
|---|---|---|---|---|
| A | 現有管線 | SHARP 點雲擬平面 | 法定標線 + 虛線碼表 | 平面來自模型 |
| B | 計畫書 | 單眼深度圖 | 法定標線 | 全部 |
| **C** | **本節** | **車道線消失點** | **虛線週期** | **零** |

### 15.2 兩個步驟,都只用標線

**① 地平線列 y_h ← 車道線消失點**(`tools/lane_line_fit.py`,既有工具)

| 段 | 左線 | 右線 | 消失點 row |
|---|---|---|---|
| seg10 | x = −1.6158y + 1211.4 (n=20) | x = +1.5445y + 0.4 (n=18) | **383.2** |
| seg21 | x = −1.4047y + 1129.1 (n=37) | x = +1.3492y + 86.2 (n=40) | **378.7** |

⚠ **地平線對抽線參數敏感**(2026-09-17 補測):預設參數得 seg10 380.3 / seg21 377.8,
`--step 1` 得 382.9 / 378.7;seg10 換 `--step` 或 `--band` 會落在 **374.9–383.4**(差 8.5 px,
20 m 處約 14%),seg21 只在 377.8–378.7 之間。本節沿用上表的值,這次只修正 A。

**② A = h·f ← 虛線在兩列之間的時間差**(`tools/vanishing_point_range_calib.py`,2026-09-17 改寫)

同一批虛線先流過遠列、再流過近列。兩列亮度訊號互相關的延遲 `lag`(幀),除以虛線流過一列的
週期 `period`(幀),再乘法定週期 14.63 m,就是兩列在路面上的實際間距;車速在 `lag/period` 裡消掉。

```
14.63 × lag / period = A · [ 1/(y_遠 − y_h) − 1/(y_近 − y_h) ]
```

每組列對給一個 A(取樣列 500 / 540 / 580 / 615,每條線 6 對)。
**單一條線的逐對散布超過 10% 就不採用**——與 `odometer_distance_calib.py` 同一道品質閘。

| 段 | 左線 | 右線 | **採用的 A** |
|---|---|---|---|
| seg10 | 1235(散布 8.6%) | 1238(7.2%) | **1238**(12 對) |
| seg21 | 1242(8.5%) | 1172(17.4%,✗ 不採用) | **1242**(6 對) |

~~舊值 1153 / 1139,「兩段吻合 1.2%,方法 C 自洽的證據」~~ → **撤回**:那個吻合是工具造成的(§18.1)。
新值兩段也接近,但**這次不把它當證據**——同一台相機本來就該接近,而上一次正是這種「接近」騙了我們。
可以當佐證的是兩件與本 benchmark 無關的事:時間差法在 2026-09-01 對雷達驗過(係數差 1.6–3.6%);
另一段 seg6(2018-07-29)上,車道寬解出的掛高 1.209 m × 該相機記載焦距 910 px = 1100,時間差法得 1104。

### 15.3 ⚠ 為什麼錨必須是「沿行進方向」的

車道寬**不能**解 A。第 py 列上寬 W_m 的車道佔 `W_px = W_m·(py − y_h)/h`,
**焦距被消掉** → 車道寬只能定掛高,`A = h·f` 的 f 仍然未知。
只有**沿行進方向**的長度(虛線週期、軸距、漆線長)才能約束 A。

這與 CLAUDE.md 記過的錯誤同型:計畫書把車牌(38×16 cm)列為距離錨,
但車牌寬度在代數上無法驗前向尺度,只能驗掛高與俯角。

⚠ **順便否證了一個看似漂亮的自洽**:用車道寬解掛高,兩段得 **1.157 m vs 1.328 m,差 13%**
——同一台車不可能。各段內部 CV 0.01% 是假的(那些 pairs 本來就是從擬合直線算出來的,
不是獨立量測)。**車道線抽取才是方法 C 的瓶頸**,與 CLAUDE.md 既有記載一致。

## 17. ✅ 度量模型的「公尺」是餵進去的焦距乘出來的(2026-09-16)

### 17.1 在解決什麼

§12.3① 主張「`metric3d_v2` 的 raw 成績好,是因為我們餵的焦距假設恰好對這台相機幾乎正確」。
那是**推論**,不是量測。`--fx` 旗標(本次新增)讓它變成量測:同一批影格、同一組目標像素,
只改餵進去的焦距。

`metric3d_v2` 與 `da3_metric` 都吃內參;預設餵的是 `fx = 0.7955 × 寬 = 926 px`。
這台相機(comma EON,1164×874)openpilot 記載的焦距是 **910 px**。

⚠ **2026-09-17 更正描述**:這裡原本把 926 px 寫成「SHARP 的固定 FOV 假設」。SHARP 的實際規則是
**30 mm 等效焦距(依對角線換算)**,16:9 畫面恰好得 0.7955 × 寬;這台 4:3 相機 SHARP 自己用的是
**1009 px(0.867 × 寬)**。本節量的是「餵 926 px」的代價,數字不受影響。

**① 模型的公尺與餵進去的焦距是嚴格 1:1。**
`k · fx/926` 這一欄在四個 fx 下**逐位相同**(1.115 / 1.008)——
也就是 `預測距離 ∝ fx`,沒有任何非線性、也沒有模型自己的判斷。
**光是換焦距就能讓 raw 誤差在 3.69% 與 37.05% 之間跑**,影像與模型一個位元都沒動。

**② 餵「正確的」焦距救不了 raw。**
讓 raw 歸零所需的 fx 是 `926 × k`,而這台相機記載的焦距是 **910**。
🔴 **2026-09-21 更正**:本節整張表是 **Δ = 2 m** 下算的,而 Δ 至今未定案(§18.4、§19.7),
所以「模型自己的偏差」必須寫成區間:

| | Δ=0 需要的 fx | 對 910 的差 | Δ=2 需要的 fx | 對 910 的差 |
|---|---|---|---|---|
| `metric3d_v2` | 937 | **+3.0%** | 1032 | **+13.5%** |
| `da3_metric` | 849 | −6.7% | 934 | +2.6% |

原文只寫 Δ=2 的「13%」並稱其「與內參無關」,那是把一個未定案參數的選擇講成模型性質。
**在 Δ 定案之前只能說 3.0–13.5%。**
仍然成立的是那句話的用途:**餵記載值 910 並沒有比較好**(Δ=2:11.86% > 10.32%;
Δ=0:3.28% > 2.34%),所以「查到正確焦距」不保證 raw 可用。

**③ 錨定之後焦距完全無關。** scaled 欄在所有 fx 下**一模一樣**(3.78 / 3.64)。

### 18.1 舊工具的 A 是讀取範圍的邊界,不是虛線

**錯在移動平均用了補零**(`np.convolve(..., mode="same")`):剖面兩端的背景被零拉低一半,
兩端就一定「亮過門檻」。統計每次被當成起點的列(每段 300 幀):

| 段 | 最常出現的六種起點對 | 相對 y_h | 佔全部配對 |
|---|---|---|---|
| seg6 | (452, 658–664) | (+60, +266–272) | 243 / 333 |
| seg21 | (438, 644–650) | (+60, +266–272) | 168 / 337 |
| seg10 | (444, 646–653) | (+61, +263–270) | 176 / 303 |

(遠列永遠是同一列 y_h+60 —— 讀取範圍的第一列。)

→ A 幾乎由 `14.63 / [1/61 − 1/268] ≈ 1140` 決定,**跟畫面內容無關**。
而假訊號比真的虛線強,把真的虛線也壓在門檻下(單幀檢查:內部一個起點都沒抓到)。

**修掉補零之後,單幀法也救不回來**:這台相機在讀取範圍內大約只看得到**一個** 14.63 m 週期,
同一幀裡很少有兩個真正的虛線起點;抓到的多半是同一段虛線的碎片,得出 A 中位 8,200–10,500(IQR 4,100–27,100,三段五條線)。
這與 CLAUDE.md 既有記載「單幀空間週期不可用(畫面裡只裝得下 2~3 個週期)」是同一個限制。

**為什麼假值會接近真值**:讀取範圍 y_h+60 ~ y_h+280 大約就是這台相機的一個週期,
所以「範圍兩端」恰好近似「一個週期的兩端」。假值 1139–1153 比時間差法的 1238–1242 低 7–9%。

**改法**:改用 `odometer_distance_calib.py` 的列間時間差(§15.2 ②)。每組列對一個獨立估計,
它們會**分散**(逐對散布 7–9%)而不是重複同一個值——這正是舊工具沒有的特徵。

### 18.2 benchmark 的「接地點」不是管線 B 的接地點

`depth_benchmark_targets.py` 的說明寫「與管線 B 定義相同」,實際上:

| | 定義 | 程式 |
|---|---|---|
| benchmark(band) | 遮罩最低 12% 列的**中位** | `depth_benchmark_targets.py` |
| 管線 B(lowest) | 遮罩多邊形的**最低點** | `dashcam_range_speed.py` |

同一批目標(`tools/contact_point_definitions.py`,567 列全部對回):

| 段 | lowest − band 中位 | IQR |
|---|---|---|
| seg10 | **8.37 px** | 6.10–12.46 |
| seg21 | **5.89 px** | 3.39–8.48 |

在 20–30 m,8 px 約等於 10–15% 的距離。band 像素**在車身上而不是路面上**,
所以把它丟進地面公式 `d = A/(py − y_h)` 會系統性算遠。舊的錯誤 A(偏低 7–9%)剛好把這個算遠抵掉,
這也是舊數字看起來很漂亮的原因之一。

⚠ 深度模型的讀值**都是在 band 像素上取的**。本次沒有在 lowest 像素上重跑五個模型;

## 19. 標線常數改定在輪胎著地點;車身中心的差距改列數值(2026-09-19,依 9/18 指導教授會議)

### 19.1 在解決什麼

9/18 會議上指導教授對 `深度模型與標線幾何_測距驗證_20260918.pptx` 提了三點:

1. 結果頁要下結論(只影響簡報,本節不處理)。
2. **「metric3d 直接輸出就很準,為什麼還要乘雷達常數?而且實際上拿不到雷達。」**
   → 主要結果應該用道路標線定的常數,雷達常數只能當參考。
3. **§14.3 那張表(方法 C 退化約 30 倍)下面寫的「無可測差異」是錯的,兩個取樣點還是有差距。**

第 2 點用 §16 的標線常數做,會碰到 §16.2 ② 的問題:當時「接地點」常數的標線距離是在
**band 像素**(遮罩最低 12% 列的中位)上算的,而 band 像素**在車身上**(§18.2),
代入只對路面成立的 `d = A/(py − y_h)` 會把距離算遠 —— Δ=0 時整個常數偏 16–18%。

### 19.2 改了什麼:標線距離改在遮罩最低點算

```
k = median( 方法 C 距離 @ 遮罩最低點 py_max  ÷  模型讀值 @ band 像素 )
```

- 模型讀值**不變**(五個模型沒有重跑,仍在 band 像素上取;§18.2 的限制照舊)。
- 只有配對用的**標線距離**從 band 列換到同一台車的遮罩最低點(`contact_defs.csv` 的 `py_max`),
  也就是輪胎與路面的接觸處 —— 公式唯一成立的地方。
- 依據:車身與它自己的著地點是同一台車,前向距離相同。⚠ 嚴格說後輪著地點在後保險桿前方約 1 m,
  這一項與相機到雷達的偏移一起歸在 Δ 裡(§18.4),本節**沒有**把它獨立出來。
- **k 的計算沒有用到任何雷達數值。** 但 §16 已記的兩處接觸照舊成立:列是由 `paired_*`
  (對雷達做過幾何一致性篩選)挑的,「近場 <32 m」也是用雷達距離分的。

工具:`python3 tools/depth_blind_analysis.py marking --delta-m 0`(與 `--delta-m 2.0`)。

## 20. 2026-09-21 重跑驗證:尺度常數改成「雷達完全不參與選樣」

### 20.1 在解決什麼
