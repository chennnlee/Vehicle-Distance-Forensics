# odometer_lag_audit — 碼表 lag 修正觸發稽核(2026-07-16)

**動機**:合成訊號測試發現「八度防護」(lag×2)與「sub-octave 修正」(lag÷2)可能互相抵銷——
sub-octave 的條件(半 lag 是嚴格局部峰且 ac≥0.6×ac[lag])在 argmax 為內部峰時幾乎必然成立,
會把八度防護剛做的加倍原樣撤銷。本稽核用 `tools/odometer_lag_audit.py`(只跑碼表、不跑 YOLO,
複現主管線雙窗合成)在五支已驗證 demo 上量測兩道修正的實際觸發頻率。

## 結論與後續

1. 八度防護+sub-octave 的「先加倍再撤銷」鏈在真實素材上以 98–100% 頻率發生——正確結果靠的是
   兩個 bug 抵銷,不是設計。應重構為一次性基頻選擇(候選 {L/2, L, 2L} 諧波評分,
   並可用已採集的 pulse x-offset 雙峰性判斷帶內是否真有第二條線)。
2. 重構後行為基準:本稽核的五案輸出(thr 無關)= 迴歸基準;20251029 批量六案(皆 thr 0.75)
   可用同工具補測。
3. per-case JSON 在本資料夾(dc002/dc003/dc006/dc007/dc008.json)。

## 2026-07-24 重構完成(一次性基頻選擇取代加倍/減半鏈)

`dash_cycle_speeds` 內的「argmax → 八度防護(×2)→ sub-octave(÷2)」鏈已換成一次性選擇:
對候選 {argmax/2, argmax, 2·argmax} 各做**諧波梳狀評分**(comb−anti:真基頻在整數倍是峰、
半整數倍是谷 → 分數高;諧波 L/2 或子諧波 2L 的半整數倍落在真峰上 → 分數低),取最高者;
其上再疊一道 **pulse x-offset 雙線偵測**——自相關對亮度無法分辨「一條線走半週期」與
「兩條交錯線走全週期」,但後者脈衝會在兩個橫向位置交替,偵測到就把真週期設為
**2×實測脈衝間距**(非 2×argmax:高速時 argmax 已在每線週期,加倍 argmax 會過修)。
`--octave-threshold` 旗標保留只為相容,已不影響選擇。
